# Risk register

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Criteria segmentation is worse than expected | High | High | [Phase 1](01-corpus-construction.md) measures it explicitly; the `unknown`-section fallback keeps unparseable trials in the corpus rather than dropping them |
| LLM cost for Phase 8 exceeds budget | High | Medium | **Now measured, not estimated: 27,045 calls for the dev set** (75 × top-20 × 18.0 criteria/trial). The "local-only, so cost is GPU hours not dollars" framing held while Phase 8 was assumed to run on Ollama — it no longer holds automatically now that Phase 4 has switched to the Gemini API (see [Phase 4](04-patient-profile-extraction.md)); **Corrected 2026-08-31: the 20/day cap is model-specific and does NOT apply to the model actually selected.** The `quotaValue: 20` seen in live 429s was measured on `gemini-3.6-flash`. Quota is documented and confirmed to be scoped *per model*, so generalising that number to `gemini-3.5-flash-lite` was an unsupported inference — made in the same note that records quota is per-model. **Counter-evidence from this repo's own artifacts:** on 2026-08-30 `gemini-3.5-flash-lite` served extraction (75 topics ÷ batch 5 = 15 calls, 23:05) *and* HyDE (75 topics ÷ batch 5 = 15 calls, 23:14) — **30 successful calls in one day on one model**, which a 20/day cap would have blocked partway through the second run. The Lite daily cap is therefore confirmed `>30`; the user reports it is **500/day**. **CONFIRMED BY LIVE 429 on 2026-09-03**, closing the open item that stood here: the Phase 8 run's own error payload names the quota exactly — `quotaId: GenerateRequestsPerDayPerProjectPerModel-FreeTier`, `quotaValue: 500`, `model: gemini-3.5-flash-lite`. So 500/day is **measured**, not reported-and-plausible, and the quota id confirms the scope is *per project per model*. The real Phase 8 workload measured 1,633 calls (not the 1,665 estimated); with 3 independent projects (see row below) 1,461 succeeded in one 2.4-hour sitting before the cap bit, leaving 172 for the next day. This reverses the earlier conclusion: **the free tier CAN run Phase 8 on the full 75-topic dev set**, so no paid tier, no cap on N, and no reduced evaluation subset is needed — the statistical power of the dev set is preserved. Model selection now carries this: `gemini-3.5-flash-lite` was chosen partly for its independent quota and 2.8x speed (10.2h vs 29.1h projected), accepting a negation-recall drop (58% vs 92%) that lands squarely on this phase — see [Phase 4](04-patient-profile-extraction.md). Batching all criteria of one trial into a single call cuts calls to **1,500 (18×)**, at the risk of the model losing track across 18 criteria; measure both. Cache on `(nct_id, criterion_idx, topic_id)`; cap N |
| Gemini free-tier quota/rate-limit exhaustion (Phase 4) | High | Low | Originally observed: all 3 round-robin keys shared one project's `generate_content_free_tier_requests` quota (5/min for `gemini-3.6-flash`), so rotation did not multiply throughput by 3. **Superseded 2026-09-03 — the keys now in `.env` belong to three INDEPENDENT projects**, confirmed by the user and corroborated by measurement: the Phase 8 run completed 1,461 calls before hitting a cap the 429 payload names as 500 *per project per model*, i.e. rotation did multiply the daily ceiling to ~1,500. The per-minute limit is still shared-in-spirit only in the sense that each project has its own; at ~10 calls/min total (6 s/pair) the run never approached an RPM limit, and every 429 seen was the *daily* quota. Mitigated in `src/extraction/gemini.py` by honoring the `retryDelay` Gemini's own 429 response returns before retrying with the next key. **A second failure mode surfaced in the real run and is now fixed:** once all three projects are exhausted, every remaining pair fails identically, but `chat_json` still tried all 3 keys sleeping up to 20 s each (~60 s per pair) while `main()` merely `continue`d — thousands of futile calls. `reason.MAX_CONSECUTIVE_FAILS = 5` now breaks the loop, saves the cache, and exits cleanly so the next day's run resumes from cache |
| Gemini API key leakage | Low | High | Keys live only in `.env` (gitignored); `.env.example` (tracked) documents the required variable names with empty values; `src/extraction/gemini.py` never logs a key. Keys pasted into a chat session should be rotated in Google AI Studio afterward — chat history is not a secret store |

| No criterion-level gold labels | High | High | Check the TrialGPT release in [Phase 0](00-ground-truth-environment.md); trial-level aggregation as guaranteed fallback |
| Dense retrieval does not beat BM25 | Medium | Low | It is a valid finding on this task; the ladder is designed to report it |
| Full-corpus encoding burns days of GPU | Medium | Medium | [Phase 5](05-dense-retrieval.md) benchmarks on a judged-plus-distractors subset before committing |
| n2c2 data-use agreement not approved in time | Medium | Low | Started in week 1; TREC alone is sufficient for the core claim |
| Integration week eats the analysis week | Medium | High | [Phase 10](10-end-to-end-system.md) forbids new component choices |
